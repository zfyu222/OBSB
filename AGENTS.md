# Second Brain vault rules

## Project discussion continuity

Before continuing product planning or implementation, read `docs/需求与方案共识.md`. It records confirmed decisions, open questions, and unverified technical assumptions. Also read `docs/Obsidian初始化配置.md` before planning or changing anything that depends on Obsidian core settings, community-plugin settings, or client permissions, and update that checklist whenever such a dependency is confirmed. The project is currently in requirements alignment. The early, unapproved plugin draft and its dependencies were removed at the user's request. Update the consensus document when the user confirms or changes a decision. Do not infer implementation or deployment authorization from earlier draft work.

This repository is an Obsidian vault and Markdown is the source of truth.

## Directory semantics

- `InBox/`: unprocessed captures. Never require the user to classify a capture.
- `Raw/项目/`: knowledge tied to a concrete outcome with an end state.
- `Raw/领域/`: durable knowledge for an ongoing subject or responsibility.
- `Raw/归档/`: completed or reference-only material.
- `Drived/整理日志/`: nightly organization reports named `YYYY-MM-DD.md`.
- `Assets/`: the single location for images and binary attachments.
- Other `Drived/` synthesis: deferred idea for conclusions synthesized from Raw notes. See `docs/需求池.md` (P01); outside the current scope.

## Agent rules

1. Read and write `.md` directly; do not move canonical note content into a proprietary database.
2. Search filenames, tags, summaries, and body text before creating a note.
3. Merge only when the new material is short or strongly overlaps an existing note. Otherwise create a focused note and link related notes.
4. Preserve facts and source links. Never invent missing provenance.
5. Before replacing an existing note, store a recoverable copy or ensure Git contains the prior version.
6. For a fully organized knowledge note under `Raw/`, require YAML `tags`, contiguous intermediate summaries `summary_1...summary_n` when any intermediate layer exists, and `summary_final`. Store the final layer only as `summary_final`, not duplicated as a numbered summary; a very short body may have only `summary_final`. Do not require `ai_managed`, `updated`, `title`, or `source`. Keep original web URLs in the relevant body location. Preserve user-defined properties such as `aliases` and never delete unknown frontmatter keys merely to normalize the note. A note with `nightly_maintenance: skip` is explicitly excluded from unattended metadata maintenance and does not require those fields until the user removes the opt-out or requests immediate organization. Nightly organization and an explicit user request to organize or finalize a non-excluded note must produce this fully organized state. An ordinary interactive body edit may defer missing or stale tags and summaries to the next nightly run; it must preserve existing frontmatter rather than deleting or mechanically rewriting it. Unprocessed Inbox notes and operational reports under `Drived/整理日志/` do not require knowledge-summary fields.
7. Summarize the body, then recursively summarize each preceding summary. Each summary is at most `min(200, floor(previous_length / 5))` normalized visible characters, so the longest summary never exceeds 200 characters, and recursion stops when `summary_final` is strictly fewer than 10 characters. Count normalized visible Unicode characters: exclude YAML frontmatter, Markdown formatting markers, and whitespace; count Chinese characters, letters, digits, and punctuation as one character each; count link labels but not raw link URLs; include code-block contents and table-cell contents. Require a rewrite rather than mechanically truncating an overlong summary. If the normalized body is already fewer than 10 characters, use it directly as `summary_final`; an empty normalized body is a processing failure. Do not assign distinct tasks to summary levels. Retrieval strategy is a separate concern.
8. Drived synthesis is deferred to `docs/需求池.md` and excluded from current implementation and nightly organization. `Drived/整理日志/` is the sole current use of Drived and contains operational reports, not synthesized knowledge. If the user reactivates synthesis later, derived notes must cite Raw sources with Obsidian wikilinks such as `[[Raw/领域/example]]`.
9. Do not edit `.obsidian/` or secrets unless the task explicitly requires it. RAG and vector indexes are deferred; do not create them in the current scope.
10. When a requested edit is ambiguous or would discard substantive content, explain the proposed merge instead of silently overwriting.
11. After successfully organizing an Inbox note, remove the source from Inbox: move the organized note into Raw or remove the source after merging its content into an existing note. Do not create an archived source copy. Preserve the prior version in Git, and keep the source if processing fails or is incomplete. This source removal is an agreed workflow and does not require routine confirmation.
12. Before choosing a destination, look for a suitable existing folder under the appropriate Raw category. Reuse it when available; otherwise, create a suitable subfolder without routine confirmation.
13. Before assigning tags, invoke the project's deterministic tag-scanning CLI through the shell to obtain existing tags from Markdown YAML frontmatter; do not read every note into model context merely to assemble the tag list. Reuse suitable names, including synonymous ones, and create a new tag only when no suitable existing tag is available. Markdown remains the source of truth; the CLI must not become a separate tag database. This does not authorize unrelated bulk retagging of the vault. Until the CLI is implemented, do not claim that automated tag assignment is production-ready.
14. Use at most 5 tags per note, usually 1–3. Tag only highly relevant core topics, not concepts mentioned incidentally. Do not add tags merely to reach a target count.
15. Nightly organization is planned for 03:00 every day in Asia/Shanghai. It processes Inbox and checks Raw notes changed since the last successful organization baseline to update tags and recursive summaries, except any Markdown note explicitly marked `nightly_maintenance: skip`. Such a note remains visible to Git baseline advancement but is not edited, moved, merged, deleted, tagged, summarized, or validated by the unattended task. Raw metadata maintenance alone does not authorize rewriting the body. Inbox merges and explicit user-requested body edits remain in scope under the existing rules. This is a product requirement; no scheduled job has been deployed yet.
16. Use Git for incremental change detection, not a separate per-file hash index. Compare the last successful nightly baseline with the complete vault state actually visible on the server at task start, including newly added and locally uncommitted notes and intervening committed changes. Do not attempt to inspect or infer edits that remain unsynced on phones or computers, and do not infer an author from Git. Inspect actual diffs and skip changes limited to AI-generated summary fields so those fields do not trigger recursive maintenance by themselves. Advance the baseline after success; never lose failed items or edits that actually arrive on the server during the run through an incorrect baseline advance.
17. When a nightly run produces note changes or encounters any failure, write `Drived/整理日志/YYYY-MM-DD.md` for quick review in Obsidian. Group the report by note rather than by action: each affected note appears once, with all actions such as created, moved, merged, metadata-updated, Inbox-source removal, or deletion combined into one concise Chinese description. Link related notes and report failed items. For a total failure, report the failed stage and unprocessed items. OpenCode provides task context, while Git provides exact diffs and recovery. Do not duplicate the full diff in the report. Only a successful run with no changes creates neither a report nor a Git commit. A failure report is committed even if no note changed, and the successful organization baseline must not advance past failed items.
18. Phase one uses OpenCode's built-in file, text-search, editing, shell, and skill tools. Search filenames, keywords, YAML tags, and all summary fields, then read candidate bodies. Do not add RAG, vector storage, custom knowledge tools, or MCP servers in the current scope. Scheduling, LiveSync, and deterministic Git orchestration remain external runtime infrastructure rather than knowledge tools.
19. Package repeatable AI workflows as Skills. A Skill handles semantic judgment and content transformation; deterministic programs validate computable constraints for unattended workflows, including YAML validity, allowed paths, tag count, recursive summary lengths, Inbox source handling, and Git/report consistency. A failed unattended validation is not success: return specific errors for at most 2 correction attempts after the initial execution. User-initiated edits in the live OpenCode session are treated like direct user edits and do not require this external gate before syncing; ordinary interactive edits should not invoke tag scanning, recursive summarization, or full Raw validation unless the user asks for immediate organization. The nightly workflow later validates and maintains affected notes.
20. Distinguish interactive and unattended writes. When the user explicitly asks the live OpenCode session to edit notes, modify the formal vault directly in that same session; prioritize the requested content change and allow Raw tags or summaries to remain temporarily stale or absent for nightly maintenance. Preserve existing metadata, sources, links, and unknown frontmatter. If the user explicitly asks to organize, finalize, tag, summarize, or validate now, complete the corresponding metadata workflow immediately. The change may sync immediately and remains a normal working-tree diff until a later snapshot or explicit commit. Do not create a child session or temporary worktree merely for that interactive edit. Nightly organization and other unattended AI writes must run in an isolated temporary Git worktree, pass deterministic validation, and be applied only when conflict checks succeed. Read-only search and Q&A use the formal vault directly.
21. Knowledge-base answers must cite sources near each material claim using Obsidian wikilinks. Prefer an existing block link (`[[path/note#^block-id|label]]`), otherwise use a heading link (`[[path/note#heading|label]]`), and fall back to the whole note only when precise positioning is unavailable. Read-only Q&A must not modify source notes merely to add block IDs. Clearly label faithful note-based content, short verbatim excerpts, AI inferences, and gaps in the knowledge base. Every inference must list its supporting note locations; never present model knowledge or inference as note content.
22. Store all images and binary attachments under `Assets/`. Agents must not read attachment contents, move, rename, or add binary attachments. Preserve existing attachment links when moving or merging Markdown notes. The sole deletion exception is an explicit user-requested standalone note deletion through `vault-ops`: after removing the note, the CLI may delete only attachments that the removed note referenced and that no remaining Markdown note references. Never perform a vault-wide orphan sweep. Attachments are synchronized and included in both backup levels but excluded from the knowledge-vault Git history.
23. In the planned production layout, the inner knowledge-vault Git repository tracks Markdown under `InBox/`, `Raw/`, and `Drived/` only. It must not track `Assets/`, `.obsidian/`, caches, temporary files, or system files. The outer framework repository is independent and ignores the entire vault; it tracks rules, documentation, Skills, helper-program source, tests, and non-secret configuration. The two repositories are not Git submodules. The current workspace has not yet been reorganized into this target layout, so do not move files merely because this rule records the approved architecture.
24. Restore knowledge by creating a new recovery commit, never by resetting the entire knowledge repository and erasing later history. Support task-level reversal and single-note restoration through a temporary worktree, preserve non-conflicting later edits, run the normal validators, and stop with a clear conflict report rather than overwriting subsequent changes.
25. In the planned nightly runtime, the Linux scheduler starts a deterministic orchestrator, which creates one named OpenCode session and one temporary knowledge-vault worktree for the run. A top-level nightly-memory-organization Skill coordinates reusable semantic Skills; the orchestrator must not start a separate OpenCode task for every tagging or summarization step. The agent may invoke the validator CLI for self-checks, but after every agent response the orchestrator must independently validate the actual worktree. Return validation errors to the same session and worktree for at most 2 correction rounds. If that session cannot be continued, fail the run rather than starting a context-free replacement session.
26. Use the deterministic `vault-ops` CLI for note reference lookup, moves, renames, standalone deletion, and post-merge source removal: directly against the formal vault for an explicit interactive user request, and inside the temporary worktree for unattended workflows. The agent supplies semantic intent and edits a merge destination first; the CLI performs structural filesystem operations, rewrites inbound wikilinks and embeds for moves, validates targets, and returns a machine-readable change list. Standalone deletion requires explicit user intent, preserves a recoverable Git snapshot, refuses to proceed while known inbound wikilinks or Markdown links remain, and applies only the limited orphan-attachment cleanup allowed by rule 22. Do not bypass it with generic move/delete commands or ad-hoc global replacements. The unattended orchestrator still runs its independent final validator.
27. At the start of an unattended write task, use the complete knowledge-vault state currently visible on the server. If visible tracked Markdown changes are not yet in Git—including direct user or interactive OpenCode edits—first create a technical server-state snapshot commit, without attributing an author or waiting for remote devices, then create the temporary worktree. Commit a successful unattended result separately. Before applying, preserve non-conflicting changes that arrived during the run and fail rather than overwrite a conflict. Interactive direct edits do not require a commit per request; they remain visible in the OpenCode session and Git working-tree diff until the next snapshot or an explicit commit request.
22. Phase-one Inbox processing handles only the literal contents of Markdown files. Treat every HTTP/HTTPS URL as body text: preserve it exactly, but do not open, fetch, validate, download, or infer the target content from its domain or path. A bare URL counts as visible body text for summary-length calculation; for `[label](URL)`, count only the visible label, not the destination. Do not read or process local or embedded PDFs, images, audio, video, Office documents, or other attachments. A URL-only capture may be organized conservatively as a saved link, but its tags, summaries, and destination must not claim knowledge of the target page.
