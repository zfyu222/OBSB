# 思维导图归纳功能设计

状态：设计草案，2026-10-12；尚未实现或发布。基于用户截图中的“括号归纳 + 概要节点”，开发基线为 Enhancing Mindmap fork `0.2.6-beta.5`。本方案保持 Markdown 为内容源，避免引入 Canvas 坐标文件。

## 目标与首版范围

选中多个分支后添加归纳括号，括号连接一个可编辑的概要节点。原节点仍保留原有父子关系，概要表示“这些分支共同得出的总结”，不是新父节点。

首版支持同一父节点下、同一布局方向、连续的两个或更多普通节点。选中父子时沿用现有顶层根过滤，再校验兄弟关系；不自动纳入没有选中的分支。同一节点首版只属于一个归纳组，跨父节点、跨左右方向、交叉或嵌套归纳暂不支持。布局顺序需按当前方向的兄弟显示顺序判断，不能用节点屏幕坐标作为持久身份。

## 用户操作

1. 左键框选或 Ctrl/Cmd 单击选择分支，从节点操作菜单运行“添加归纳”，也提供 Obsidian 命令入口。不替换当前 Tab/Enter 等快捷键。
2. 在分支外侧出现括号和默认“概要”节点，立即进入文字编辑。允许空内容；结束编辑后可撤销、重做。
3. 双击概要编辑正文；单击概要或括号选中归纳关系。Delete 删除归纳及其概要，不删除被归纳的分支。
4. 概要按布局自动定位；首版不支持独立拖动或向概要添加普通子节点。选择被归纳的分支仍使用已有批量移动、删除、复制功能。
5. 右键拖动画布与左键框选继续使用 beta.5 行为。归纳菜单优先通过现有操作菜单或命令面板提供，避免右键平移和菜单冲突。

## Markdown 保存

推荐把概要正文写在附近的 Obsidian callout 中；节点身份及成员关系用 HTML 注释保存。示例是新语法草案，当前 beta.5 不能按此语法识别归纳。

```md
# 预测修正

- 单位式回滚 <!-- mm:node {"id":"n-a"} -->
  - 直接回滚
- 回滚重放 <!-- mm:node {"id":"n-b"} -->
  - 固定帧模拟
  - 非固定帧重放

> [!summary] 概要
> <!-- mm:summary {"version":1,"id":"s-1","members":["n-a","n-b"]} -->
> 两种方案都通过回滚修正预测结果，但恢复过程不同。
```

成员 ID 的含义是“概要归纳哪些节点”，不记录 x/y、宽高或 SVG 路径；位置从节点布局计算。正文就在相关内容附近，Markdown 阅读时能看到分支和总结，AI 也能明确区分成员关系与内容。callout 内可以容纳多段正文、图片、代码或表格，按原始 Markdown 保存；图上仍用 Obsidian MarkdownRenderer 渲染。标题作为概要名称，正文作为概要内容；编辑器要同时暴露标题和正文。

只有具有 `mm:summary` 标记的 callout 才是归纳，其余 callout 维持普通内容。只给参与归纳的普通节点持久化 `mm:node` ID，创建关系时补齐标记，不给全篇笔记强制添加 ID。解析时先提取关系和 ID 标记，再将普通节点正文送入已有 Transformer，避免把注释显示在节点中、把 callout 当作普通子树。

现有 `^id` 被插件当成折叠标记，不能直接拿来替代新的稳定 ID。迁移时普通节点运行时身份以 `mm:node` 为准，另行读取现有折叠标记；保存后可统一折叠标记与稳定身份，旧文件仍按旧逻辑导入。必须增加“稳定 ID 但未折叠”的测试，不能因加入归纳导致节点折叠。

首版不承诺修复所有普通节点的多段 Markdown 保存问题。概要 callout 使用独立的正文提取和序列化，不经过现有会丢弃段落的节点清理逻辑；未来普通节点完整 Markdown 正文可复用这部分设计。

## 关系与修改规则

运行时新增独立 `Summary` 集合，每条关系包含 `id`、`memberIds`、`title`、`bodyMarkdown` 和语法版本。普通节点的 `parent/children` 不变；概要参与可见元素测量、选择、命中检测和导出，但不参与普通树的层级遍历。关联父节点、方向和位置均从成员推导。

| 操作 | 归纳行为 |
| --- | --- |
| 改文字、尺寸或折叠成员 | 重算括号及概要位置；成员的隐藏后代不参与可见包围盒 |
| 折叠成员的共同父节点 | 归纳随成员隐藏；重新展开恢复 |
| 在已有成员之间插入普通兄弟 | 首版不自动扩大归纳范围；GUI 插入或移动不得使原归纳跨过未选中节点，应将新节点放到归纳组边界外，并给出原因提示 |
| 删除部分成员 | 移除相关引用；剩一个成员时保留概要，避免自动丢失已写的总结 |
| 删除全部成员 | 同一删除命令中移除归纳和概要；撤销完整恢复正文、引用和节点 |
| 将部分成员移出归纳组 | 从归纳中移除这些成员，保留其余成员；完整移动整组时归纳随组移动 |
| 同一父节点下重排造成归纳跨过其他节点 | GUI 拒绝此次无效重排，保留历史；提示先移出归纳或整组移动，不悄悄扩大成员集合 |
| 复制子树或多个分支 | 仅携带全部成员都包含在复制范围内的归纳；新建关系及成员 ID，重映射引用；重复/跨图粘贴仍独立 |
| 单独复制概要 | 复制概要正文为普通文本；不产生指向外部成员的悬空归纳 |
| 删除归纳 | 只删除关系和概要，原分支不变 |

所有关系及普通树的联动改动都放进同一个命令事务，不能依靠渲染时副作用修复引用，否则 Ctrl+Z 会恢复不完整。已有粘贴命令需要扩充 payload，并兼容只有 `copyNode/copyNodes` 的旧剪贴板。

用户或 AI 手工编辑 Markdown 后若 ID 重复、引用缺失、成员不再同父/连续，则保留概要原文和原始关系标记，显示明确的修复提示；不能静默删掉或猜测指向其他节点。涉及未解析关系的编辑应使用保留原始片段的序列化方式；不能用当前全树重写方式覆盖掉它们。用户可显式解除关联后把概要作为普通文本保留。

## 自动布局

先测量普通节点及概要的实际渲染尺寸，归纳组在布局测量阶段就预留空间，再进行排布。不能只在现有布局完成后覆盖画括号，长概要会与相邻分支重叠。

- 每个组取成员可见子树的联合包围盒；右向分支在右侧外缘画括号，左向分支在左侧外缘画括号，效果对应截图。
- 括号从组的上缘延伸到下缘，预留固定间距；概要连接括号中点，镜像布局保持一致。
- 将括号、间距和概要宽高计入组的布局占用空间，再由下到上的测量影响祖先与相邻组。概要比组高时，以两者较大的高度参与排布。
- SVG 括号使用独立 group；用图内坐标绘制，随已有缩放及平移，不持久化视口坐标。文字、图片异步渲染结束后清除相关布局缓存并重排。
- `getBoundingRect`、居中、导出图片/SVG 和框选命中检测都应包含可见概要；普通树命令只接受普通节点选择集，避免误把概要当成子树根。

## 实施顺序与验收

1. **先完成保存层**：独立的标记/callout 提取及序列化；稳定节点 ID；正常文件兼容；未知或无效关系原文保留。用 round-trip 测试确认不改节点层级和正文。
2. **再实现关系命令**：创建、编辑、删除归纳；普通删除/移动/复制粘贴与关系的原子联动；撤销/重做。
3. **最后实现 UI 和布局**：选中分支添加归纳、概要编辑、左右括号、预留空间、折叠可见性和导出。完成后再选新 beta 版本，不把设计文档当作已经可用的功能。

重点测试：创建→保存→关闭重开；空概要及多段正文/图片/表格/代码保存；长文本防碰撞；左/右/双侧布局；折叠→展开；删除部分/全部成员及一次撤销；整组移动及跨图复制；部分复制不带悬空关系；ID 重复、缺失或手工改结构时保留原文；视图切换不丢关系；发布 bundle 与浏览器交互。最终还需在 Obsidian 客户端检查原文编辑、Markdown 阅读、关系菜单和附件渲染。

主要代码入口：`MindMapView.setViewData/mdToData`（提取与导入）、`MindMap.getMarkdown`（保存）、`INode`（身份与渲染）、`Layout`（测量和括号）、`Cmds/Execute/History`（事务）、`clipboard.ts`（引用重映射）。建议把保存格式与关系模型放入独立模块，避免继续堆进已有较长的 `mindmap.ts`。
