## 1. 原始产品需求

1. 笔记软件仍使用 Obsidian，主要存储格式必须是 Markdown。
2. 多设备同步，用户已有 Linux 服务器。
3. 随手记进入 `InBox/`，不要求用户立即分类；整理后的知识进入 `Raw/`。`Drived/整理日志/` 用于保存自动整理报告；最初提出的 Drived 综合推导功能已移入需求池，当前暂不考虑（见 D19、D23）。
4. 每篇笔记支持标签，AI 可以自动打标签。
5. 支持多级摘要：AI 对正文生成摘要，再持续对上一层摘要进行摘要；每级最多为上一层实际字数的 1/5，且任何一级摘要都不超过 200 字，直到最终少于 10 字。不为各层分配不同任务。
6. 使用独立通用 Agent，通过 Skills、rules、必要的 MCP 和文件搜索管理笔记。
7. 第一期使用关键词、标签和摘要检索；RAG 语义搜索已移入需求池（见 D27）。
8. AI 能基于知识库问答。
9. 记忆整理：读取 Inbox，分类、打标签、生成摘要；短小或与已有文章高度相关的内容可以合并。
10. 用户可以自然语言要求任意合理的笔记操作，不限于固定功能，例如将 Inbox 内容直接合入已有文章的某个章节。

目录名称沿用用户截图；当前只使用 `Drived/整理日志/`，综合推导功能仍属于后期需求：

```text
Vault/
├── InBox/
├── Raw/
│   ├── 项目/
│   ├── 领域/
│   └── 归档/
├── Drived/
│   └── 整理日志/          # 夜间整理报告
└── Assets/                # 所有图片及二进制附件
```

## 2. 已确认的方案决策

| 编号 | 决策 | 边界与原因 |
| --- | --- | --- |
| D01 | 复用 Obsidian | 原生编辑、Markdown、目录、标签、链接与搜索不需要重新开发。 |
| D02 | Agent 从第一阶段起运行在 Linux 服务器 | 手机和电脑通过网页交互；不依赖个人电脑开机。 |
| D03 | 使用 OpenCode Web | 作为交互入口和 Agent 运行环境，替代此前的 NanoBot 主方案。 |
| D04 | 同步完全自托管 | 不依赖 Obsidian 官方服务器，不支付 Obsidian 同步费用；不等于要求模型推理免费。 |
| D05 | 采用 Self-hosted LiveSync + CouchDB + LiveSync CLI | 手机/电脑使用现成同步插件；CLI 将服务器文件目录与同步数据库双向同步。具体版本和部署方式待验证。 |
| D06 | 所有使用端保有真实 Markdown 文件 | Obsidian 和 Agent 直接读写 `.md`；CouchDB 额外保存内容与同步元数据，用户已理解并接受这一点。 |
| D07 | AI 修改直接生效并自动同步 | 修改正式 vault 后由同步服务传播；不以逐项审批或接受 diff 作为生效条件。 |
| D08 | 变更用于事后查看 | 用户只需知道 AI 做了什么，不设置逐项审批。查看入口由 D23 确定。 |
| D09 | 知识库 Git 用于修改账本、恢复和增量变化识别 | 内层知识库仓库在服务器按 Agent 任务记录，修改前保留基准；结合 D21 识别待整理变化。不参与设备同步，不要求 GitHub，也不按每次保存或输入一个标点提交。外层框架仓库的职责由 D41 单独规定。 |
| D10 | 支持夜间自动记忆整理 | 早上能够查看结果和变化；执行时间、范围和报告位置已由 D20～D23 确定。 |
| D11（被 D95 修订） | 自研 Obsidian 插件暂非第一阶段前提 | 第一阶段先使用 OpenCode Web；后续发现明确交互缺口时再讨论插件。 |
| D12 | 继续对齐需求，再实施 | 本次文档整理不构成开始实现、安装、连接服务器或部署的授权。 |
| D13 | 多级摘要采用连续摘要规则 | 正文 → 摘要 → 摘要的摘要，逐层继续；每层字数 ≤ 上一层实际字数的 1/5，同时任何一级摘要绝对不超过 200 字，直到最终 < 10 字。不规定层数或各层的特定任务。 |
| D14 | 摘要生成规则与召回策略分开 | Agent 可以按关键词搜索，也可以查看所有笔记的摘要进行召回；不为配合某一种检索流程给摘要层级分工。具体召回策略仍可独立讨论。 |
| D15 | Inbox 整理成功后移除原文 | 独立成篇时整理并移动到 Raw，合入已有文章时移除 Inbox 源文件；不另存原文归档副本。Git 保留整理前版本以供恢复。整理失败或未完成时保留源文件。 |
| D16 | 分类时优先复用已有目录 | 先在 Raw 对应分类下查找合适的已有目录；没有合适目录时，AI 可自行创建子文件夹。 |
| D17 | 标签优先复用，必要时新增 | 打标签前通过 D39 的标签 CLI 获取已有标签；有合适或同义标签时使用已有名称，没有合适标签时 AI 可自行新增。此规则不等于默认批量重写全库历史标签。 |
| D18 | 标签少而精，每篇最多 5 个 | 通常 1～3 个，仅标与文章核心主题高度相关的标签，不标偶然提到的概念，不为凑数量打标签。 |
| D19 | Drived 综合推导功能移入后期需求池 | 用户尚未想清楚，当前暂不讨论或实现，不纳入夜间整理。`Drived/整理日志/` 的运行报告不属于综合推导功能。详细设想见 `需求池.md` 的 P01。 |
| D20 | 夜间整理同时维护发生变化的 Raw 笔记 | 除处理 Inbox 外，通过 D21 识别自上次成功整理后发生变化的 Raw 笔记，按已确认规则更新标签和多级摘要；不按自然日或文件修改时间截断。此项元数据维护不包含主动改写正文；Inbox 合并或用户明确要求的正文修改仍按原有规则执行。 |
| D21 | 用 Git 基准版本识别增量变化 | 记录上次夜间整理成功的 Git 版本，与本次整理前快照比较，包含期间已提交及当前尚未记录的变化。查看实际 diff，跳过仅由 AI 摘要字段变化造成的重复维护。无需另建逐文件 hash 索引。全部成功后推进基准；失败不能被基准推进遗漏。 |
| D22（被 D93 修订） | 每日 03:00 调度转为后续可选项 | 原计划为 `Asia/Shanghai` 每日 03:00 运行。2026-09-22 用户确认当前正式交付为手动完整整理版，不创建或维护 DSM 定时任务；若将来重新启用，必须单独确认并复用 D93 的完整流程。 |
| D23 | 通过三个入口查看 Agent 变更 | `Drived/整理日志/` 用于早上快速浏览；OpenCode Web 用于查看任务会话和执行过程；Git 用于精确文件 diff 与恢复。三者记录同一任务的不同层次。 |
| D24 | 有变化或失败时按运行时间生成整理日志 | 夜间任务或手动完整整理产生笔记变化或发生失败时，由确定性编排器唯一写入 `Drived/整理日志/YYYY-MM-DD-HHMMSS.md` Markdown 报告，并在正文写明运行时间；同一天的多次运行各保留独立报告。报告按笔记归并：每篇受影响笔记只出现一次，用一句自然、简洁的中文综合说明实际处理结果，不展示“新建、移动、更新元数据”等内部动作标签，也不机械罗列 YAML 字段；移动已包含离开 Inbox，不另说“移除 Inbox 来源”，未改变的常规事项不写。报告链接相关笔记，并另列真正的失败及需注意事项；完整逐行 diff 留给 Git/OpenCode。纯失败也生成报告。 |
| D25 | 只有成功且无变化的夜间任务静默结束 | 没有 Inbox 可整理、没有 Raw 内容需要更新且任务无错误时，不生成空报告、不创建 Git 提交，并保持现有整理基准。失败属于需要记录的事件，不适用静默规则。 |
| D26 | 失败写入整理日志且不推进成功基准 | 部分失败时在同一份报告中同时记录成功变化与失败项；全部失败时报告错误、失败阶段和未处理内容。失败项对应的成功整理基准不得推进，以便后续重试。失败报告作为实际记录同步并进入 Git 历史。 |
| D27 | RAG 语义搜索移入需求池 | 第一期不部署向量数据库、Embedding 或语义索引。先使用文件名、关键词、标签和各级摘要召回，再读取候选正文。实际证明文本召回不足时重新评估，详见需求池 P02。 |
| D28 | 第一期不开发 MCP 或通用知识检索服务 | 知识库读取、搜索、编辑、移动和 Git 操作主要使用 OpenCode 内置的 `read`、`grep`、`glob`、`edit`、`write`、`apply_patch`、`bash` 与 `skill`。允许通过 shell 调用职责单一的确定性 CLI，包括 D39 的标签扫描和 D29 的校验程序；这类程序用于压缩机械工作和验证约束，不承担语义判断，也不是 RAG 或另一套知识库。同步、调度和 Git 基准管理仍属于外围运行设施。 |
| D29 | 可复用工作流封装为 Skills，无人值守结果由程序校验 | Inbox 整理、标签、摘要、合并、问答等工作流可分别封装为 AI Skills。Skill 负责语义判断和内容处理；确定性程序负责 YAML、路径、标签数量、摘要字数等可计算约束。凌晨整理等无人值守任务必须通过外部权威校验，失败时返回明确错误供 Agent 修正。用户在实时 OpenCode 会话中明确要求的直接编辑视同用户编辑，不以外部校验作为同步前门禁；后续夜间整理再检查并维护相关笔记。 |
| D30（被 D74 修订） | 临时 Git 工作区不再用于所有写入任务 | 原决定要求每个写入型 Agent 任务都先进入临时 worktree。为保持交互简单，D74 将其缩小为凌晨整理、恢复及其他无人值守写入；用户明确发起的实时会话编辑直接写正式 vault。 |
| D31 | 知识库回答必须引用笔记及对应位置 | 每个基于知识库的关键陈述都附 Obsidian wikilink。默认使用 `[[路径/笔记#标题|显示文字]]` 定位到章节；已有稳定块 ID 时使用 `[[路径/笔记#^块ID|显示文字]]` 定位到段落；只有无法可靠定位时才退回整篇笔记链接。只读问答不为创建引用而修改源笔记。 |
| D32 | 回答必须区分笔记内容与 AI 推断 | 忠实复述或概括笔记时标为“笔记内容”并就近引用；超出笔记明确表述的综合、判断或建议标为“AI 推断”，同时列出支撑链接。直接逐字引用时标为“原文摘录”。知识库证据不足时明确说明，不把模型常识伪装为笔记内容。 |
| D33 | 第一期 Inbox 只处理 Markdown 本身，不访问外部链接内容 | Agent 读取 `.md` 文件中的字面正文；其中的 HTTP/HTTPS URL 只是正文的一部分，必须原样保留，但默认不打开、不抓取、不检查可访问性，也不根据域名、路径或页面标题猜测链接后的内容。普通链接、登录页、失效链接及指向 PDF/图片等资源的 URL 均按同一字面文本规则处理，不因无法访问而判定整理失败。本地或嵌入附件仍不由第一期 AI 读取或处理。 |
| D34 | 摘要长度按规范化后的可见正文字符计算 | 不统计 YAML frontmatter、Markdown 格式标记和空白；中文、字母、数字和标点均按 1 个 Unicode 字符计数。Markdown `[显示文字](URL)` 只计算实际可见的显示文字，链接目标不计；直接写在正文中的裸 URL 属于可见字面正文，按实际字符计入，但 AI 不读取其目标内容。代码块内容和表格单元格内容计入。每层上限为 `min(200, floor(上一层计数 / 5))`，即最长摘要也不得超过 200 字；超限时要求 AI 重写而非机械截断。正文少于 10 个字符时直接作为 `summary_final`，不再强行压缩；空白正文处理失败、保留 Inbox 源文件并写入整理日志。 |
| D35 | 第一期使用云端模型推理，计划接入 DeepSeek API | OpenCode 在服务器上运行并通过用户配置的 API 调用 DeepSeek，不要求在 Linux 服务器本地部署推理模型。Markdown 与同步服务仍为自托管；“数据自托管”不等于“推理不出服务器”。具体 DeepSeek 模型、接口地址、调用预算和密钥配置在实施设计时确定。 |
| D36 | 第一期不设置 AI 禁读目录 | Agent 可以读取整个 vault，并按任务需要将相关内容发送给 DeepSeek。敏感笔记隔离、路径/标签禁区和发送前脱敏属于后期隐私保护需求，已移入需求池 P03，当前不实现。 |
| D37 | 无人值守校验失败后最多自动修正 2 次 | 凌晨整理及其他走外部校验管线的任务包含首次执行及最多 2 次根据明确错误进行的自动修正，总计最多 3 次尝试。三次仍不合格即停止，不把临时结果应用到正式 vault；Inbox 源文件保持不动并按规则写失败报告。用户实时会话中的直接编辑不触发该自动重试管线。 |
| D38 | 元信息与正文保存在同一个 Markdown 文件中 | 强制元信息字段由 D59 规定，写在笔记顶部的 YAML frontmatter，由 Obsidian 作为 Properties 展示；不创建独立 YAML 元数据文件。第一期不开发摘要展开或专用展示功能，只在 Agent rules、Skills 和格式校验中定义字段含义。 |
| D39 | 第一期提供本地标签扫描 CLI | 由确定性程序实时遍历 Markdown、解析 YAML frontmatter，并把去重后的已有标签结果提供给 Agent；Agent 不自行读取所有笔记来汇总标签，以降低上下文负担和 Token 消耗。首期提供 `tags list` 与 `tags search <关键词>` 两类接口，紧凑返回标签名和使用次数，支持 JSON 等机器可读格式。Agent 通过 OpenCode 的 shell 工具调用。第一期不做持久缓存；程序不保存另一份标签事实源，不属于 RAG、MCP 或特殊知识库服务，标签事实仍来自 Markdown。实际扫描性能不足时再考虑可重建缓存。 |

## 3. 工作流程与存储职责

### 日常交互

用户在手机或电脑浏览器打开 OpenCode Web → 下达笔记操作指令 → 服务器 Agent 搜索并读写 Markdown → 记录任务变更 → LiveSync 自动同步 → 用户在 Obsidian 阅读，在任务记录中查看变化。

### 完整记忆整理（手动）

用户在 OpenCode `workspace` 输入 `/run-nightly` → 保存当前笔记的整理前快照 → 与上次成功整理版本比较 → 处理 Inbox 和需要更新元数据的 Raw 笔记 → 生成 `Drived/整理日志/YYYY-MM-DD-HHMMSS.md` → 保存整理结果和变更说明 → 成功后推进整理基准。正式 vault 的文件修改和整理日志自动同步，用户可在 Obsidian 查看报告。

当前不设置自动执行时间。DSM 每日 03:00 调度已转为后续可选项（D22、D93）；如将来重新启用，必须单独确认且复用现有确定性编排程序。变更查看有三个入口（D23）。

夜间整理范围已确认：处理 Inbox，并检查自上次成功整理后发生变化的 Raw 笔记，更新标签和多级摘要（D20、D21）；不包含 Drived 综合推导功能。Raw 元数据维护不意味着主动改写正文。

### 各组件职责

| 组件 | 内容与职责 |
| --- | --- |
| 手机和电脑 vault | 普通 `.md` 与附件，供 Obsidian 编辑和阅读。 |
| Linux 正式 vault | 普通 `.md` 与附件，供 Agent 操作，也是服务器的同步工作副本。 |
| CouchDB | 保存 LiveSync 使用的笔记内容分块、元数据等数据库记录；不是只保存文件路径。 |
| LiveSync CLI | 连接服务器 vault、内部同步数据库和 CouchDB。内部数据库与真实 vault 是不同概念。 |
| Obsidian 客户端 | 只运行在手机和电脑上，负责编辑、属性界面、渲染与链接跳转；服务器不启动 Obsidian。 |
| 外层框架 Git | 保存 Agent 规则、文档、Skills、辅助程序、测试与非敏感配置的版本；其更新不影响知识库历史。 |
| 内层知识库 Git | 保存选定时点的知识库版本，支持任务 diff、恢复和增量变化识别；不是每次敲字都记录。 |
| 未来 RAG 索引 | 已移入需求池 P02；第一期不存在。未来若采用，必须可由 Markdown 重建。 |

### 目标目录与双 Git 边界

生产环境采用一个 OpenCode 项目根目录、两个彼此独立的 Git 仓库。外层仓库通过 `.gitignore` 忽略整个 `vault/`；`vault/` 自身拥有独立 `.git/`，但不作为正式 Git Submodule。OpenCode 从外层根目录运行，LiveSync CLI 只同步 `vault/` 的知识内容并排除 `vault/.git/`。

```text

├── .git/
├── AGENTS.md
├── docs/
├── skills/
├── tools/
├── config/
├── tests/
└── vault/                    # Obsidian vault、内层知识库 Git
    ├── .git/
    ├── .obsidian/
    ├── InBox/
    ├── Raw/
    ├── Drived/
    └── Assets/
```

缓存、运行状态和临时知识库 worktree 放在正式项目之外的运行目录。凌晨整理、恢复及其他无人值守写入只对内层知识库仓库建立 worktree 和提交；用户在 OpenCode 当前会话中明确要求的笔记修改直接写正式 vault。框架规则或工具开发只提交外层仓库。两类变更不要求形成跨仓库原子提交，也不因内层提交而更新外层指针。

### 变更查看入口

| 入口 | 用途 |
| --- | --- |
| `Drived/整理日志/YYYY-MM-DD-HHMMSS.md` | 手机或电脑在 Obsidian 中快速查看某次整理处理了什么、哪些项目失败或需要注意。 |
| OpenCode Web | 查看对应任务的对话、执行过程和 Agent 说明；定时任务会话如何稳定关联尚需验证。 |
| Git | 查看精确的逐行文件差异，并在需要时恢复。它是最终可追溯记录。 |

三个入口互补，不要求三处重复保存完整 diff。整理日志应记录能够定位对应 OpenCode 任务和 Git 版本的信息，具体字段在实施设计时确定。只有“成功且无变化”时不新增报告或 Git 提交；失败即使没有成功修改任何笔记，也要生成失败报告并进入 Git 历史。

同步路径：服务器 Markdown ↔ LiveSync CLI ↔ 自托管 CouchDB ↔ 各设备 LiveSync 插件 ↔ 各设备 Markdown。

这仍是双向同步：用户可在手机和电脑编辑。服务器是 Agent 的固定工作位置，不意味着服务器版本可以无条件覆盖客户端修改。

手机离线或应用挂起时不保证立即收到更新；打开 Obsidian 并完成同步后显示最新内容。

### Git 的记录粒度

无人值守 Agent 任务在任务前保留服务器状态快照，并为成功结果建立独立提交。用户主动要求的实时 AI 编辑视同用户直接编辑，不按每次请求强制提交；OpenCode 会话展示其过程，Git 工作区展示相对 `HEAD` 的累计 diff。下一次凌晨整理开始前，将服务器当时可见的全部未提交 Markdown 作为技术快照纳入 Git；用户也可以明确要求立即提交。

恢复应保留用户后来做的修改，不能简单把整个 vault 回退到旧状态。服务器同时发生同步写入与 Agent 写入时，需要技术上区分变化来源。

### Git 增量整理基准

已确认采用以下方案，而不另外维护逐文件内容指纹索引：

1. 保存“上次夜间整理成功时的 Git 版本”，作为增量整理基准。它与单次任务的修改前快照用途不同。
2. 夜间开始时，比较当前服务器笔记状态，包含新增文件与尚未提交的笔记变化；只有实际需要记录变化时才创建提交。无变化时复用现有版本，不创建空提交。
3. 比较整理基准与本次快照，识别新增、修改、移动的 Raw 笔记，不能只看工作区未提交的变化。已删除的笔记不恢复为待处理笔记。
4. 检查实际内容差异，跳过仅 AI 摘要字段变化造成的重复维护；正文或标签变化交给 AI 检查是否需要更新。
5. 记录整理结果，全部成功后推进基准。部分失败时在报告中记录失败项，且不得推进会覆盖失败项的成功基准；失败项留待后续重试。基准的具体表示方式在实施设计时确定。

此方案按版本差异识别内容变化，不声称能仅凭 Git 准确判断修改者身份，也不尝试查询客户端尚未同步的状态。任务只以启动时服务器可见状态为准；延迟同步的手机编辑在实际到达服务器后纳入冲突检查或下一次比较。生产 vault 从空库建立初始基准；任务运行中新增同步变化仍需在应用阶段检查，避免把尚未处理的变化计入成功基准。

### 备份等级与范围

项目本身不调度或执行备份，只为用户的第三方备份工具说明包含与排除范围。

**等级一：最小知识备份**

- 包含 `vault/InBox/**/*.md`；
- 包含 `vault/Raw/**/*.md`；
- 包含 vault 中的全部附件；目标结构采用 `vault/Assets/**` 集中存放时，直接包含整个 `Assets/`；若实际存在其他附件目录，也必须纳入，不能只依赖扩展名猜测；
- 不包含 Git 历史、整理日志、程序、配置和运行状态。

该等级保证核心 Markdown 及其附件仍在，不保证恢复修改历史、AI 运行报告或完整运行环境。

**等级二：完整可恢复备份**

- 包含 `vault/InBox/`、`vault/Raw/` 和 `vault/Drived/` 中不可由其他文件重新生成的正式内容，包括 Markdown、来源附件和 AI 生成的整理日志；
- 包含外层框架仓库的 `.git/` 和内层知识库仓库的 `vault/.git/`，分别保留系统版本与知识历史、任务 diff 和恢复能力；
- 包含 `AGENTS.md`、`docs/`、后续正式使用的 Skills、确定性程序源代码及不可重建的配置；
- 若需要保留 Obsidian 使用习惯，包含 `.obsidian/` 中用户配置和插件配置数据，但不包含工作区缓存、插件缓存或可重新安装的构建产物；具体白名单在实施时根据实际文件确认；
- API 密钥及其他秘密不混入知识备份，应由用户的秘密管理或独立安全备份方案处理。

即使在完整级别也排除以下可推导或临时内容：CouchDB 中可由正式 vault 重新建立的同步副本、LiveSync CLI 内部同步状态、未来的 RAG/向量索引、标签扫描缓存、OpenCode 缓存、临时 Git worktree、依赖目录、构建产物、下载缓存、运行时锁文件和普通运行临时日志。依赖清单及其版本锁定文件属于正式项目源文件，不在排除范围。`Drived/整理日志/` 是需要保留的正式 AI 运行记录，不按普通运行日志排除。

完整备份的目标是恢复知识、历史和项目规则，不是制作服务器系统镜像。第三方工具如何做快照、加密、保留周期和异机复制由用户自行管理。

内层知识库 Git 不跟踪图片、PDF、音视频及其他二进制附件。Git 负责 Markdown、YAML 元信息和整理日志的可读 diff、历史与回滚；附件的同步由 LiveSync 负责，版本保护和恢复由第三方备份负责。

### Skill 与程序校验的分工

第一期分为两条模式：

- 用户主动交互：`用户在当前 OpenCode 会话下达指令 → Agent 直接修改正式 vault → LiveSync 同步 → 夜间任务后续检查发生变化的 Raw 或处理 Inbox`。它视同用户直接编辑，不创建子会话或 worktree，不以外部校验作为同步前门禁。普通正文编辑默认延迟标签、摘要和完整 Raw 校验；只有用户要求立即整理或校验时才在交互会话完成这些元数据步骤。
- 无人值守写入：`DSM 调度/恢复任务 → 编排程序创建临时 Git worktree 和 OpenCode Session → 总 Skill 组织子 Skill → 程序独立权威校验 → 最多两轮修正 → 合格后自动应用 → Git 提交并同步`。临时工作区用于自动质量控制和冲突隔离。

适合放在 Skill 中的内容包括：判断主题、选择目录、复用标签、判断新建还是合并、组织正文、生成摘要、说明修改原因。适合程序校验的内容包括：

- Markdown 与 YAML frontmatter 能否解析，必需字段是否存在；
- 文件路径是否位于允许目录，是否误改 `.obsidian/` 或秘密文件；
- 标签是否去重、数量是否不超过 5；
- 每层摘要是否按 D34 的统一计数规则不超过 `min(200, floor(上一层长度 / 5))`，最终是否严格少于 10 个字符；
- 合并成功前是否保留 Inbox 源文件，成功后是否按规则移除；
- Git 任务记录、整理日志及成功基准是否一致。

移动、重命名和合并收尾位于两者之间：Agent 决定语义目标并在需要时完成目标正文，`vault-ops` CLI 负责实际文件操作与全库引用更新，将变更清单立即返回给 Agent。AI 不应手工搜索替换路径，也不能自行删除合并源文件来绕过该程序。

“标签是否真的相关”“合并是否语义合理”“摘要是否忠于原文”不能仅靠机械校验保证，仍由 Agent 按 Skill 处理，并通过实际案例验证。D37 规定无人值守任务首次执行后最多自动修正 2 次，仍未通过则不应用临时结果并按失败处理。

### 交互直写、临时工作区与正式写入

用户在 OpenCode Web 当前会话中主动要求修改时，Agent 直接编辑正式 vault，变化可以立即由 LiveSync 下发。它仍须遵守内容规则，移动、重命名和合并收尾仍通过 `vault-ops`，但不为该请求创建另一会话或 worktree，也不等待夜间校验才生效。修改先保留为 Git 工作区 diff，下一次无人值守任务前统一建立技术快照。

无人值守写入和恢复采用 Git worktree，流程如下：

1. 写任务开始时记录正式 vault 的基准版本，并为任务创建临时 worktree。
2. Agent 只在临时 worktree 中修改；LiveSync 不监控该目录，因此中间状态不会下发到设备。
3. Agent 可以在工作过程中调用校验 CLI 自查；Agent 返回后，程序必须独立执行一次权威格式和业务硬约束校验。
4. 不合格时，程序把机器可读错误发回原 OpenCode Session，在同一 worktree 中最多自动修正 2 次；每轮结束后由程序重新权威校验。
5. 校验通过后，确认正式 vault 自基准以来是否收到新变化。没有冲突时自动应用；有不相交的变化时合并；同一内容发生冲突时不覆盖，任务记为失败或留待重试。
6. 正式写入成功后生成整理日志、提交 Git，并让 LiveSync 自动同步。失败时丢弃临时内容；夜间任务仍按 D26 写入失败报告。

worktree 将无人值守写入风险限制在应用阶段，并避免未通过校验的自动结果被同步。并发合并的具体实现仍待实施设计；自动修正上限已由 D37 确认为两轮。

### 知识库问答与引用

回答采用以下语义标记：

- **笔记内容**：笔记明确记载的信息，可以忠实概括；关键陈述后附章节或块链接。
- **原文摘录**：确有必要逐字展示的短片段，使用引用格式并紧跟来源链接。
- **AI 推断**：由多处笔记综合、推导出的结论或建议，必须显式标记，并列出推断所依据的笔记位置。
- **知识库未覆盖**：检索不到足够依据时明确说明；若补充一般知识，也必须与知识库内容分开标示。

笔记中存在一个外部 URL 只能证明笔记保存了该链接，不能证明链接目标页面包含什么。第一期知识库问答不得自动访问这些 URL，也不得把模型对域名或 URL 路径的猜测作为笔记证据；只有用户另行明确要求联网查看时，才作为独立的联网任务处理，并与知识库内容分开。

定位优先级为“已有块链接 → 标题链接 → 整篇笔记链接”。示例：`[[Raw/领域/检索/RAG#混合检索|RAG：混合检索]]`。Obsidian 支持标题和块级内部链接；块引用属于 Obsidian 特有语法。第一期的只读问答不会为了更精细的定位而给源文件新增块 ID。OpenCode Web 是否能将 wikilink 或 `obsidian://` URI 渲染成可点击并唤起移动端 Obsidian，需要实际验证；即使网页不支持，链接文本复制或保存到 Obsidian 后仍可使用。

### Inbox 输入边界

第一期只扫描和处理 `InBox/` 中的 Markdown 文件。正文里的普通 HTTP/HTTPS URL 与其他文字相同，作为字面正文保留；Agent 不发起网络请求，不读取目标页面，也不判断链接是否有效。URL 本身不是目标页面内容的证据。

本地或嵌入的 PDF、图片、音频、视频和 Office 文档不在第一期自动处理范围。指向这些资源的 URL 仍只是普通文本，不会触发下载或附件处理。如果 Inbox 只有 URL 而没有任何说明，Agent 可以保留和整理这个链接条目，但标签、摘要与分类只能依据明确可见的字面文本；信息不足时必须明确保持保守，不能臆测链接内容。

## 4. 知识库维护规则

以下细则保存在按需读取的 [知识库维护详细规则](知识库维护规则.md)；根目录 `AGENTS.md` 只保留日常任务的短入口：

- 创建笔记前搜索文件名、标签、摘要和正文。
- 只有内容短小或高度重叠时才合并，其他情况创建聚焦的笔记并建立链接。
- 保留事实、原有价值和来源；不虚构出处。
- 修改现有笔记前保存可恢复版本。
- 整理完成的 Raw 知识笔记强制使用 YAML `tags`、连续的中间摘要 `summary_1...summary_n`（若有）和 `summary_final`；不强制 `ai_managed`、`updated`、`title` 或 `source`，并保留用户其他属性。
- 连续对上一层进行摘要；每层最多为 `min(200, floor(上一层实际字数 / 5))`，最终严格少于 10 字；不为各层规定不同任务。
- Drived 综合推导功能已移入后期需求池；当前只使用 `Drived/整理日志/` 存放运行报告。引用 Raw 来源的约定仅在未来启用综合推导功能时适用。
- 不随意修改 Obsidian 配置、生成索引或密钥。
- 指令含糊或会丢弃实质内容时说明拟议合并，不能静默覆盖。

正常明确任务直接生效，与最后一条处理歧义的规则不冲突；不应因此添加普遍的审批流程。
