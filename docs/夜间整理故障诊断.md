# 夜间整理故障诊断

适用范围：在 OpenCode `workspace` 项目中用 `/run-nightly` 手动触发的完整整理。日常 OpenCode 直接编辑笔记不使用这条运行管线。

## 正常结果

- `success`：已整理并应用变化；有变化时在 `Drived/整理日志/YYYY-MM-DD-HHMMSS.md` 生成本次报告，并创建知识库 Git 提交。
- `no_changes`：没有需要处理的内容；不生成报告、不创建提交，这是正常结果。
- `failed`：正式 vault 未应用本次 worktree 的整理结果；失败报告会写入 `Drived/整理日志/`，成功基准不会推进。
- `startup_failed`：任务在创建隔离工作区前无法启动；查看任务计划输出或容器状态，再修复后重试。

## 常见提示

### `another nightly run is already active`

已有一项夜间任务仍在执行。等待其结束后再试，不要手动删除 `runtime/nightly/nightly.lock`。

如果 NAS 或 `brain-agent` 在任务中意外重启，下一次任务会验证锁记录的进程是否仍存在；确认原进程已消失后会自动回收残留锁和临时 worktree。

### `formal vault changed concurrently`

任务运行时，同一篇笔记刚好从 Windows、Android 或交互式 OpenCode 会话同步到服务器。正式内容会被保留，本次夜间结果不会覆盖它。

等待同步稳定后手动重试。不要通过强制 Git 操作覆盖该笔记。

### `validation failed`

Agent 已获得最多两轮修正机会，但最终结果仍不符合 Markdown/YAML、标签或递归摘要规则。查看当日整理报告中的错误项；原始 Inbox 内容与正式 Raw 笔记都保持原样，可直接在 OpenCode 中要求修复或下次重试。

### `nightly task modified a note marked nightly_maintenance: skip`

某篇笔记声明了 `nightly_maintenance: skip`，夜间任务不允许触碰它。保留该属性并从本次候选中排除，或在你希望恢复自动维护时移除该属性后再运行。

## 查看运行状态

在 NAS SSH 中执行以下只读检查：

```sh
sudo /var/packages/ContainerManager/target/usr/bin/docker ps --filter name=brain-agent
sudo /var/packages/ContainerManager/target/usr/bin/docker inspect brain-agent --format '{{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{end}}'
```

在 OpenCode `workspace` 项目输入 `/run-nightly` 会启动完整编排流程，而不是直接编辑正式 vault；结果会直接返回 JSON。整理内容与失败原因优先查看 Obsidian 中的 `Drived/整理日志/`，精确差异和恢复点查看内层知识库 Git。

## 恢复与重试原则

- 中断或失败不会推进成功基准；下一次正常运行会重新看到未完成的变更。
- 成功后需要撤销时，使用 `restore-vault-history` 的预览和恢复流程，创建新的恢复提交；不要使用仓库级 `git reset`。
- 不要手动修改 `runtime/nightly/nightly-state.json`、`nightly.lock` 或 `/worktrees/nightly`。这些运行状态由编排程序自动维护。
